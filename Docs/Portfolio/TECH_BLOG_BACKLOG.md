# RODI 기술 블로그 작성 목록

## 목적

RODI 구현·문제 해결 경험 중 기술 블로그로 작성할 소재와 검증 상태를 관리한다. 각 소재는 실제 구현·검증 근거와 후속 작업을 함께 남긴다.

## Core Location·Live Activity 글의 작성 범위

GPS 판정은 별도 글로 분리하지 않고 첫 번째 글의 `코스 주행 여부를 어떻게 판단할까`에서 함께 다룬다.

- 수평 정확도가 기준을 벗어난 좌표를 제외한 이유
- 수신 시각이 오래된 위치 표본을 현재 위치로 사용하지 않는 이유
- 표본 사이의 시간과 최대 이동 속도로 비정상적인 순간이동 거리를 제거하는 방법
- 현재 좌표가 경로 주변 corridor 안에 있는지 판정하는 과정
- 현재 진행률이 전체 polyline 완주율이 아니라 유효 이동 거리 기반 완료 조건 진행률이라는 한계
- 정상 주행·코스 주변 통과·이탈 후 재진입의 실제 결과

## Swift 6 Migration 글의 제목과 대주제

**제목:** Swift 6는 왜 동시성 버그를 컴파일 에러로 만들었을까?

**부제:** 마이그레이션을 통해 다시 이해한 데이터 레이스, 격리와 Swift Concurrency

1. Swift는 왜 동시성 안전성을 언어가 책임지려 했는가
2. Swift 6가 컴파일 단계에서 잡겠다는 것은 정확히 무엇인가
3. 컴파일러는 코드가 안전한지 어떻게 판단하는가
4. 마이그레이션 오류는 기존 코드의 어떤 설계 문제를 드러내는가
5. 실제 대응 사례로 이해하는 격리 경계
6. 컴파일 에러를 없애는 것과 동시성 문제를 해결하는 것은 다르다
7. Swift 6도 잡아주지 못하는 동시성 문제
8. Swift 6 Migration이 결국 요구하는 것은 스레드 처리가 아니라 소유권 설계였다

글의 중심 문장은 다음과 같다.

> Swift 6 Migration은 컴파일 오류를 제거하는 작업이 아니라, 기존 코드에서 암묵적이었던 상태의 소유권과 동시성 경계를 언어가 이해할 수 있도록 다시 설계하는 작업이었다.

## Live Activity 강제 종료 글의 작성 기준

- MUST 문제를 위치 수집이 멈춘 뒤에도 Live Activity가 진행 중으로 남는 정합성 오류로 정의한다.
- MUST Apple이 앱 프로세스와 Live Activity의 수명을 분리한 이유와 `staleDate`가 즉시 종료 기능이 아닌 점을 먼저 설명한다.
- MUST 단순 `Task` 호출이 프로세스 종료 전에 완료되지 못하는 흐름을 보이고, 종료 전용 `nonisolated` 경계가 MainActor 교착을 어떻게 피하는지 연결한다.
- MUST 제한된 세마포어 대기가 Apple이 보장하는 해법이 아닌 best-effort 우회라는 한계를 명시한다.
- MUST 종료 콜백이 오지 않는 crash·watchdog·suspended 상태를 숨기지 않고, 다음 앱 실행 시 sessionID로 고아 Activity를 정리하는 복구 정책을 함께 다룬다.
- MUST Swift 6 안전성을 `@MainActor` 상태 미캡처, Sendable 경계, Strict Concurrency 정적 검사로 구분해 제시한다.
- MUST 실기기 결과를 OS·종료 직전 앱 상태·반복 횟수·즉시 제거 성공 여부로 표에 기록하고, 측정하지 않은 버전은 추정하지 않는다.
